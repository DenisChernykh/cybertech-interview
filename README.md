# Лист — внедрение онлайн-оплаты в существующий магазин

Небольшой законченный учебный проект для технического собеседования. Сначала создан работающий магазин косметики с ручной обработкой заказов, затем отдельными коммитами добавлены онлайн-оплата, возвраты, контроль чеков и восстановление после сбоев.

В проекте два платёжных адаптера: локальный `MockPaymentProvider` и HTTP-интеграция с официальным API ЮKassa v3 в тестовом режиме. Реальных списаний нет. Настоящие фискальные документы не формируются. HTTP-адаптер покрыт контрактными тестами; результаты подключения внешнего тестового магазина и ограничения проверки приведены в [VERIFICATION.md](VERIFICATION.md).

## Быстрый запуск

Нужны Docker с Compose и Python 3 для создания локальной конфигурации:

```sh
python3 scripts/init-env.py
docker compose up --build -d
```

- Магазин: http://localhost:8080
- Менеджер: http://localhost:8080/manager
- Тестовые письма Mailpit: http://localhost:8026
- Проверка API: http://localhost:8080/api/health

Пароль менеджера создаётся в локальном `.env`, переменная `MANAGER_PASSWORD`. Скрипт не перезаписывает существующую конфигурацию. `.env` исключён из Git. Порты опубликованы только на loopback; интернет-публикация не настроена.

Адрес отправителя задаётся переменной `SMTP_SENDER`. В локальном Compose письма по-прежнему принимает Mailpit; он не доставляет их на внешние адреса. Настройки сервера для настоящей отправки описаны в [инструкции по развёртыванию](deploy/README.md).

Остановка с сохранением данных: `docker compose stop`. Повторный запуск: `docker compose up -d`. PostgreSQL хранит заказы в именованном томе. `docker compose down -v` удаляет этот том — для обычного перезапуска эта команда не нужна.

Подсеть Compose задаётся `SHOP_SUBNET`, по умолчанию `10.246.73.0/24`. Если она занята, выберите свободную подсеть в `.env`. Первой сборке нужен доступ к реестрам Docker, npm и Python. Версии зависимостей закреплены в `uv.lock` и `pnpm-lock.yaml`; базовые образы указаны в Dockerfile.

## Как выполнить оплату и возврат

1. Добавьте товар в корзину, укажите вымышленные имя, email и адрес, оформите заказ. Сервер фиксирует состав, цены, доставку 300 ₽ и резерв на 30 минут.
2. Нажмите «Оплатить». Откроется локальная страница с явной пометкой Mock; банковская карта не нужна. Подтвердите оплату.
3. На странице заказа появится подтверждение, отдельно — состояние тестового чека. В Mailpit появится письмо о платеже. Состояние регистрации чека не означает его доставку покупателю.
4. Войдите как менеджер. Фильтр «Можно комплектовать» показывает заказы с подтверждёнными деньгами. Доступны комплектация, передача в доставку и подтверждение получения. Последнее создаёт тестовый чек полного расчёта с зачётом предоплаты.
5. Для возврата выберите оплаченный заказ **до отправки**, нажмите «Вернуть всю оплату» и укажите причину. В Mock отдельно подтвердите или отклоните результат возврата. После отказа доступен повтор; при неизвестном результате новый возврат заблокирован.
6. Если заказ уже комплектовали, отдельно подтвердите «Товар возвращён на полку». Денежный возврат не увеличивает складской остаток автоматически.

Обычную отмену оплаченного заказа покупателем должен подтвердить менеджер в части возврата денег. Для оплаты, пришедшей после отмены заказа, система сама создаёт обязательство и попытку полного возврата. В Mock результат этой попытки задаётся демонстрационной кнопкой менеджера.

## Негативные сценарии

| Сценарий | Как воспроизвести | Ожидаемый результат |
|---|---|---|
| Двойное нажатие оплаты | Повторить запрос оплаты одного заказа; конкурентный вариант есть в Pytest | Одна активная попытка, один внешний платёж |
| Банк отказал | «Отклонить платёж» на странице Mock | Отказ виден покупателю, можно повторить до окончания исходного резерва |
| Закрыта страница | Открыть оплату, закрыть вкладку, вернуться через «Мои заказы» | Существующую оплату можно продолжить; второй платёж не создаётся |
| Нет webhook | Раскрыть «Проблемные сценарии», отметить «Не доставлять webhook», подтвердить | Фоновая проверка обнаружит платёж обычно в пределах минуты; браузер для этого не нужен |
| Повторные/поддельные webhook | Автоматические HTTP- и PostgreSQL-тесты | Тело уведомления не меняет деньги; состояние берётся через API, побочные действия не дублируются |
| Сервер недоступен | `python3 scripts/check-outage.py` при работающем Compose в Mock | API и worker действительно останавливаются; после запуска потерянное подтверждение восстанавливается |
| Последний товар покупают двое | Конкурентный PostgreSQL-тест | Только один заказ получает резерв, остаток не отрицательный |
| Резерв истёк | В заказе менеджера «Завершить резерв · Mock» | Неоплаченный заказ отменён, резерв освобождён; проверка денег продолжается |
| Деньги после отмены | Оставить страницу Mock открытой, отменить заказ в другой вкладке, затем подтвердить оплату | Заказ остаётся отменённым, автоматически создаётся полный возврат |
| Возврат отклонён | «Отклонить возврат · Mock» | Открытая проблема, причина отказа, повтор только после известного отказа |
| Ошибка чека | В Mock выбрать «Ошибка регистрации» | Оплата сохранена, комплектация разрешена, отправка заблокирована; «Касса восстановлена · Mock» моделирует исправление внешним сервисом |

После изменения Mock-возврата без webhook можно дождаться очередной сверки либо нажать «Проверить операции». Это запрос проверки, а не ручная установка успешного статуса. Уведомления, операции и намерения отправить письма сохраняются в PostgreSQL.

## Тестовый магазин ЮKassa

В `.env` задайте `PAYMENT_PROVIDER=yookassa_test`, `YOOKASSA_SHOP_ID` и `YOOKASSA_SECRET_KEY` из **тестового** магазина. Приложение принимает только ключи с префиксом `test_`; боевого режима нет. Платежи также проверяются по `test=true` и идентификатору магазина.

Для проверки входящих webhook нужен доступный по HTTPS адрес приложения. Настройте `PUBLIC_URL`, соответствующий `TRUSTED_ORIGINS` и `COOKIE_SECURE=true`, а в ЮKassa укажите `https://ваш-домен/api/webhooks/yookassa`. Подпишитесь на `payment.succeeded`, `payment.canceled`, `refund.succeeded`. У возврата с отказом нет отдельного используемого здесь webhook: его обнаруживает периодический GET. После изменения `.env` пересоздайте API и worker: `docker compose up -d --force-recreate api worker`. Сначала завершите активные Mock-сценарии; старые записи сохраняются.

В тестовом магазине откройте «Настройки → Онлайн-касса», включите режим проверки чеков и в вопросе «Что делать с платежом, если чек не доставлен?» выберите **«Принимать платёж»**. Именно этот пункт соответствует сценарию API «Платёж и чек одновременно»: данные передаются в `receipt` вместе с платежом, ошибка регистрации чека контролируется отдельно. «Не связывать платёж и чек» требует другого сценария API и для этой реализации не подходит. [Описание сценариев ЮKassa](https://yookassa.ru/developers/payment-acceptance/receipts/54fz/other-services/basics).

Получить тестовые реквизиты и карты: [официальная инструкция ЮKassa](https://yookassa.ru/developers/payment-acceptance/testing-and-going-live/testing). В тестовом режиме чек не отправляется в ОФД как настоящий фискальный документ. Для проверки внешнего контура нужны реальные тестовые реквизиты, настройки webhook и выбранной кассы — локальные тесты их не заменяют.

Если публичный HTTPS-адрес пока недоступен, можно проверить оплату и возврат с `PUBLIC_URL=http://localhost:8080`: покупатель возвращается в локальный магазин, статусы получает фоновая сверка через API. Это не подтверждает доставку webhook. При смене провайдера старые платежи сохраняют свой источник; Mock-действия выключены в режиме ЮKassa.

При использовании VPN проверяйте доступность API и всех сервисов платёжной страницы. В проверенном прогоне потребовался прямой маршрут для `api.yookassa.ru`, `yoomoney.ru` и его поддоменов, включая `static.yoomoney.ru`, `paymentcard.yoomoney.ru` и `fl.yoomoney.ru`. Недоступность статики давала пустую форму, а недоступность сервиса карты — сообщение о техническом сбое. Перед повторной оплатой проверяйте сохранённую попытку через API; при `pending` продолжайте её, при подтверждённом отказе создавайте новую в пределах резерва.

## Локальная разработка и проверки

Python 3.13, uv 0.13.6, Node 24 (>=24.18.0), pnpm 11.15.1. Не запускайте локальный API и контейнерный API одновременно для обычной разработки. API и worker используют один backend; Redis, Celery и брокер сообщений не нужны.

```sh
python3 scripts/init-env.py
docker compose stop api worker frontend
docker compose up -d db mail
cd backend
uv sync
uv run alembic upgrade head
uv run python -m app.seed
uv run uvicorn app.main:app --port 8019
```

В другом терминале из `backend`: `uv run python -m app.worker`. Из `frontend`: `pnpm install`, затем `pnpm dev`. Интерфейс доступен на http://localhost:5179. Для ссылок в письмах при локальной разработке задайте `PUBLIC_URL=http://localhost:5179`.

Серверные тесты используют отдельную PostgreSQL, не SQLite:

```sh
# Из корня: создать один раз; существующую shop_test повторно не создавать.
docker compose exec db createdb -U shop shop_test
cd backend
DATABASE_URL=postgresql+psycopg://shop:local-demo-only@localhost:55439/shop_test uv run alembic upgrade head
uv run pytest -q
uv run ruff check app tests ../scripts
uv run ruff format --check app tests ../scripts
uv run alembic check
```

`TEST_DATABASE_URL` переопределяет тестовую БД. Тесты очищают таблицы только БД с суффиксом `_test`; не задавайте туда рабочую БД. По умолчанию используется локальный пароль из `.env.example`; при его изменении скорректируйте обе строки подключения. Провайдер в Pytest принудительно Mock, запросы к ЮKassa подменены на уровне HTTP-транспорта.

Автоматические браузерные проверки требуют работающего приложения с `PAYMENT_PROVIDER=mock` и создают демонстрационные заказы в его БД. После изменения провайдера пересоздайте API и worker, как указано выше. Эти сценарии используют локальные кнопки Mock; внешнюю платёжную страницу ЮKassa проверяют отдельно:

```sh
cd frontend
node --version
pnpm --version
pnpm install
pnpm exec playwright install chromium
BASE_URL=http://localhost:8080 pnpm test
pnpm build
pnpm format:check
```

Для Vite можно опустить `BASE_URL`; значение по умолчанию — `http://localhost:5179`. Пароль менеджера браузерные тесты читают из `.env` или переменной окружения. Скриншоты сохраняются в `artifacts/`, отчёты и трассы не попадают в Git. Перед проверкой перезапуска остановите локальный worker, если запускали его вне Compose. Пример проверки реального перезапуска: `python3 scripts/check-outage.py` из корня. Она временно останавливает только API и worker этого Compose-проекта, затем восстанавливает их и возвращает тестовую оплату.

## Что реализовано и где смотреть

- Каталог четырёх товаров, корзина, оформление с проверкой расчёта и конкурентным резервом.
- Гостевая сессия покупателя, отдельный вход менеджера, проверка прав на сервере, Origin-защита изменяющих запросов.
- Неизменяемые денежные снимки, Decimal/NUMERIC, блокировки PostgreSQL, идемпотентность.
- Реальный тестовый адаптер ЮKassa, независимый Mock-реестр, устойчивые попытки операций, webhook-inbox, периодическая сверка с пагинацией.
- Полные возвраты с историей попыток, отдельные состояния чеков, контроль ошибок и тестовые письма.
- Интерфейс менеджера с историей, проблемами, разрешёнными действиями и свежестью сверки.

## Ограничения и следующий шаг для реального бизнеса

- Нет регистрации, восстановления гостевого доступа после удаления cookies, частичных возвратов и возвратов после отправки; один склад и одна валюта. Показаны последние 200 заказов менеджера/100 заказов покупателя, полноценная пагинация UI вне MVP.
- Скидки в модели предусмотрены, но промо-движка нет: демонстрационная скидка нулевая. Ставка НДС демонстрационная, единая; реальные налоги, маркировка косметики, ФФД, касса и ОФД требуют настройки с ответственным за учёт.
- После 23 ч 55 мин неизвестный POST больше не повторяется. Платёж с потерянным ID может восстановиться сверкой по метаданным; неоднозначный возврат остаётся проблемой для разбора в кабинете провайдера. В MVP нет интерфейса ручной привязки неизвестного возврата и формирования корректирующего чека.
- Письмо со статусом `accepted` принято SMTP-сервером, но доставка покупателю не доказана. При падении после SMTP-приёма возможен повтор письма; денежные действия при этом не повторяются.
- Сверка API подтверждает состояние платежей и возвратов, но не банковские выплаты на расчётный счёт. Для промышленной эксплуатации нужны сверка реестров/выплат, мониторинг обязательств, сроки реакции и ответственный сотрудник.
- Перед внешним запуском нужны тесты с реквизитами ЮKassa и кассой, HTTPS, индивидуальные аккаунты менеджеров, ограничение попыток входа и входящих webhook, безопасный reverse proxy, резервные копии с проверкой восстановления, управление секретами и персональными данными, CI и контроль обновлений зависимостей.

Граница проекта — демонстрационный магазин и проверяемые бизнес-сценарии. Включение боевых платежей требует отдельной реализации и приёмки.
