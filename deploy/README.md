# Подготовка демонстрационного сервера

Деплой запускается вручную через GitHub Actions → **Deploy demo → Run workflow** из `main`. Перед публикацией выполняются проверки CI и сборка интерфейса. Само создание репозитория или push не запускает деплой.

Конфигурация рассчитана на отдельный VDS Ubuntu, PostgreSQL, nginx и процессы systemd без Docker. API слушает только `127.0.0.1:8000`. На сервере установлены Python 3.13, `uv` 0.13.6, отдельная база и пользователь `cybertech`. Настройки приложения хранятся в `/srv/cybertech/shared/demo.env`, а не в Git. Этот файл задаёт `DATABASE_URL`, `MANAGER_PASSWORD`, `PUBLIC_URL`, `TRUSTED_ORIGINS`, `COOKIE_SECURE` и тестовый платёжный режим Mock. Значения должны корректно читаться и shell, и systemd EnvironmentFile.

Unit-файлы установлены; пользователь `cybertech` может через sudo только перезапускать API и worker указанной командой. Фронтенд собирается на GitHub; сервер устанавливает Python-зависимости из `uv.lock`. Для домена настроен сертификат Let's Encrypt с продлением через webroot.

Для реальной отправки VDS использует локальный Postfix (`SMTP_HOST=127.0.0.1`, `SMTP_PORT=25`) и релей NetAngels `skvmrelay.netangels.ru`. Адрес отправителя задаётся через `SMTP_SENDER`; для демонстрации выбран `noreply@shop.strelchukgo.ru`. OpenDKIM подписывает исходящие сообщения ключом, который хранится только на сервере. Для проверки отправителя необходимо опубликовать SPF и DKIM в DNS поддомена и проверить фактическую доставку. Принятие письма локальным Postfix не гарантирует его доставку получателю. Mailpit на `127.0.0.1:1026` остаётся отдельным локальным вариантом для тестирования без внешней доставки.

В GitHub Actions требуются переменные `DEPLOY_HOST`, `DEPLOY_USER` и секреты `DEPLOY_SSH_KEY`, `DEPLOY_KNOWN_HOSTS`. Ключ деплоя должен быть отдельным от административного, а ключ сервера — проверенным по независимому каналу. Скрипт создаёт новый каталог релиза, применяет миграции и начальные данные, переключает ссылку `current`, перезапускает API и worker и проверяет их состояние. При сбое перезапуска или проверки он возвращает предыдущую ссылку, если она существовала. Миграции базы автоматически не откатываются; перед изменением схемы нужно отдельно предусмотреть восстановление данных. Старые релизы сами не удаляются.

Пользователю `cybertech` нужны права записи в `/srv/cybertech`, `incoming` и `releases`. Если файл `/srv/cybertech/deploy.lock` уже существует, он также должен быть доступен этому пользователю на запись. Workflow **Check demo server** проверяет эти права: созданная от `root` блокировка может иначе остановить активацию даже при исправном SSH.

**Статус:** сервер подготовлен; первый деплой и сквозная проверка приложения ещё не проводились. Отдельный workflow **Check demo server** проверяет доступ из GitHub и основные предпосылки, не развёртывая приложение.
